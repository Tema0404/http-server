# HTTP сервер на C++20
Учебный HTTP сервер для Linux, написанный без использования сторонних библиотек. Один поток обслуживает множество клиентов через epoll, сокеты и дескриптор epoll обернуты в RAII-классы, маршруты регистрируются через `std::function`. 
## Возможности
- Мультиплексирование соединений через `epoll` (level-triggered), один поток
- RAII-обёртки над файловыми дескрипторами: `socket_wrapper`, `epoll_wrapper`
- Регистрация маршрутов с обработчиками-лямбдами
- Отдача статических HTML-страниц, ответы 404 для неизвестных путей и отсутствующих файлов
- Корректная отправка больших ответов (цикл с учётом частичной отправки, `MSG_NOSIGNAL`)
- Один запрос на соединение
## Требования
- Linux
- Компилятор с поддержкой C++20
- CMake 3.16+
## Запуск
```bash
cmake -S . -B build
cmake --build build
./build/server
```
Сервер слушает `127.0.0.1:7545`. Откройте в браузере:
- [http://127.0.0.1:7545/](http://127.0.0.1:7545/)
- [http://127.0.0.1:7545/about](http://127.0.0.1:7545/about)
## Пример использования
Пример из `main.cpp`:
```cpp
#include "http.h"
#include <memory>
#include <filesystem>

int main(){
    std::filesystem::path root = std::filesystem::path(PROJECT_ROOT) / "html_pages";

    auto server = std::make_unique<HTTP_server>("127.0.0.1:7545");

    server->handle_http("/", [&](HTTP_req& req){
        server->parsehtml_http(req.fd, root / "index.html");
    });
    server->handle_http("/about", [&](HTTP_req& req){
        server->parsehtml_http(req.fd, root / "about.html");
    });

    server->listen_http();   // бесконечный цикл
}
```

Обработчик получает `HTTP_req` с методом, путём, протоколом и ссылкой на клиентский сокет.

## Архитектура
Проект разбит на слои, каждый зависит только от нижележащего:

| Слой      | Класс            | Ответственность                                                                                                                                          |
| --------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Системный | `socket_wrapper` | Владение дескриптором сокета, обёртки над `bind`, `listen`, `accept`, `send`, `recv`. Закрывает fd в деструкторе, копировать нельзя, можно перемещать    |
| Системный | `epoll_wrapper`  | Владение дескриптором epoll, `add_fd`, `wait`                                                                                                            |
| Сетевой   | `net_server`     | Слушающий сокет, `accept` новых клиентов, хранение принятых соединений в `unordered_map<int, socket_wrapper>`, выдача готовых к чтению fd (`wait_ready`) |
| HTTP      | `HTTP_server`    | Роутинг, разбор запроса, формирование ответов                                                                                                            |
| HTTP      | `http_parser`    | Разбор адреса `ip:port` и первой строки запроса                                                                                                          |
## Жизненный цикл запроса
1. `net_server::wait_ready()` ждёт события в `epoll_wait`. Если готов слушающий сокет, принимает клиента и регистрирует его в epoll. Для остальных событий возвращает список готовых fd
2. `HTTP_server::listen_http()` для каждого готового fd достаёт сокет через `get_conn()`, читает запрос и разбирает первую строку (метод, путь, протокол)
3. `switch_http()` находит обработчик по пути и вызывает его. Обработчик отправляет ответ через `parsehtml_http()` или `send_response()`
4. Соединение закрывается через `close_conn()`: сокет удаляется из карты, деструктор закрывает fd, epoll снимает его автоматически

Владельцем клиентских сокетов является `net_server`, наружу выдаются только ссылки.
## Правила роутинга
- Сначала ищется точное совпадение пути
- Если его нет, берётся префикс до второго `/`: запрос `/about/team` будет обработан обработчиком `/about`
- Иначе возвращается `404 Not Found`

Закрытием соединения управляет только `listen_http()`. Обработчики сокет закрывать не должны
## Ограничения
Проект учебный, и сейчас у него есть некоторые ограничения:
- Запрос читается одним вызовом `recv` (до 2048 байт). Длинные заголовки или запрос, пришедший в нескольких TCP-сегментах, обрабатываются некорректно
- Нет таймаутов: клиент, подключившийся и не приславший данные, держит соединение, пока не уйдёт сам
- Отправка блокирующая: клиент, медленно читающий большой ответ, задерживает остальных
- Парсер запроса не проверяет формат строки (нет ответа 400) и игнорирует метод (нет 405). Query string (`/about?x=1`) не отделяется от пути
- Нет keep-alive: каждый запрос открывает новое соединение
- Только IPv4, адрес разбирается через `inet_addr`
- Заоголовки запросов не разбираются
